## Why the scripts end in `.txt`

`filesync.json` has `"scriptsFolder": "."`, `"allowedFiletypes": [".js"]` and `"pushAllOnConnection": true`. So every `.js` file under this repo folder gets pushed into the game, including ones in subfolders. A plain copy of the scripts in `Melissa/scripts/` would land in the game as `Melissa/scripts/orchestrator.js` and so on, duplicating about 100 files on home. They would not use RAM unless run, but they would use disk and clutter the file list, and a wrong `run` would start an old copy.

So every `.js` is stored as `name.js.txt` here, which the sync ignores. `.old` backups and `filesync.json` are copied as they are. To use a file, rename it back (drop `.txt`) and put it in the main folder.

## What is copied, and what is not

`Melissa/scripts/` mirrors the main folder: the top-level scripts, `go/`, `hack/`, `utils/`, `tools/exploits/` and `old/` (the backups from before each change).

Left out on purpose:
- `passwords.json`, `vault_found.txt`, `scout_nodes.txt`: live game data and darknet passwords. Do not put these on GitHub.
- `NetscriptDefinitions.d.ts`: 377 KB and regenerated by the sync.

Nothing was moved, deleted or edited in the main folder.

## Changes and why

### Batcher (`hack/batcher.js`, `lib-target.js`)
Rewritten on 2026-11-03 to be much smaller in RAM (about 10.8 GB per the notes) and to take timings from the game's own hack, grow and weaken time functions. Only the 100 ms gap between landings is a fixed value. Income after the rewrite is unverified. A separate thread is evaluating feedback on it and was waiting on a `[Status]` line from you.

### Orchestrator (`orchestrator.js`)
Keeps the helper scripts running and decides from live state what to launch. Reports why a script cannot be placed in `placement-why.txt`. Changes this week: the idle loop went from 60 s to 20 s, logic-based home RAM and core spending (see below), a guaranteed early TOR/programs purchase, and start-of-run `boot` handling for Bladeburner. After changing it you must `kill orchestrator.js` and run it again.

### Timings shortened (review thread, 12:32)
Augmentation plan rebuild 20 min to 5 min (also when cash is 25% above what the last plan saw, or after an install). Plan and verdict staleness limit 40 to 15 min. Rep goals 10 to 5 min. Income log 5 to 2 min. Auto-backdoor retry 3 to 1 min (ready) and 10 to 5 min (nothing ready). `reset-compare.js` now reads the reset overhead, max wait, run limit and speed factor from the same config as the plan instead of its own copies. Why: you said timings seemed slow, and a stale plan was delaying decisions.

### Logic instead of fixed tables
- **Home RAM and cores** (`upgrade-home-ram.js`, `upgrade-home-cores.js`): buy when the cash left still covers 2 minutes (RAM) or 5 minutes (cores) of measured income. The old 50% and 25% shares remain only as a fallback when there is no income reading.
- **NeuroFlux** (`utils/nf-rule.js`): leftover cash buys a level only when no home upgrade is affordable.
- **Crime** (`crime-pass.js`): each crime is scored by chance x (karma + weight x exp) / seconds. The exp weight drops to 0 once the best karma crime has a 75% chance or better.
- `homeRamBuying` and `homeCoresBuying` were removed from `config.js`. Backups are in `old/*.before-logic.js.old`.

### BitNode 4 "destroy" work (node-eta, reset logic)
- **`node-eta.js`** estimates the fastest route to destroy the node by simulating reset by reset (multipliers compound across resets), and prints "unknown" instead of a wrong number. The route model is inlined in it; `utils/route-model.js` is kept as reference only. Backups: `node-eta.before-*` in the project's `bn4-singularity/backup/` folder.
- **Reset logic** (`reset-compare.js`, `augs-plan.js`, `buy-augs.js`): fixed a 60-minute wait window and a guaranteed reset when a run is 4 h or longer and the batch is at least x1.5.
- **`auto-destroy.js`** acts on the verdict. Auto-reset is on; `run reset-now.js --auto off` turns it off.
- **Findings so far:** hacking 9000 needs many resets, income in BN4 is roughly 40x weaker, and Bladeburner at a 12% success chance is slow.

### Bladeburner and combat (`bb-manage.js`, `bb-pass.js`, `faction-pass.js`, `crime-pass.js`)
`bb-manage.js` decides a state (`off`, `boot`, `train`, `run`) from live state and follows `bb-route.txt`, which `node-eta.js` writes. Before this, only the augmentation weights read the route and the Bladeburner state machine ignored it. On the hacking route it now holds, so faction, company and hacking work get the player's time. Combat training, the gym and Bladeburner actions are owned in one place so the passes do not fight over the player. I did not re-check the exact ownership rules line by line for this README; read `bb-manage.js` and `faction-pass.js` headers for the current rules.

### All factions, aug dataset, city factions
- `faction-goals.js` and `faction-pass.js` used to consider only factions in the config order. They now cover every joined faction (config order first, then nearest goal).
- `aug-dataset.js` writes `aug-dataset.txt` every 10 minutes: one row per augmentation across all factions, with price, rep needed, estimated time, impact, value per cost and the reason it was chosen or skipped.
- **City factions** used to be skipped on purpose because joining one bars its rivals. As of 18:13 they are part of the decision: the value of a city faction's augs minus the value of what its enemies would have given, join the best if the net is positive, and travel to the best city only when the invite needs nothing you do not already have. The plan no longer picks factions that bar each other (it used to list "join Volhaven" and "join Sector-12" as steps 1 and 2).
- Not done: the plan treats the city invite as a step to pick, not a goal that drives travel. (The decision code now lives in `city-pass.js`, see the review fixes above.)

### Independent review fixes (2026-11-03, after the first snapshot)
A separate thread reviewed the day's BN4 changes against the backups and the v3.0.1 API and fixed six bugs. None of it has been run in the game. Backups are `old/*.before-indep.js.old` (`faction-pass`, `node-eta`, `orchestrator`).
- **City logic moved to a new `city-pass.js`.** The city-faction code had roughly doubled `faction-pass.js` from about 20 GB to about 41 GB of RAM, and that script decides what you do every minute. `faction-pass.js` is now back down (12 KB source, from 16 KB).
- **Two city-choice flaws fixed.** With a Sector-12 invite pending (which happens whenever you have $15m there), it never left Sector-12 for the better Chongqing group. And after joining Sector-12 it would never take Aevum. `city-pass.js` now compares the groups that can be joined together, joins only the best one, and waits while Bladeburner's route is not settled. After about 5 minutes `cat city-why.txt` shows its reasoning.
- **Faction work skips factions that refuse work** (Bladeburners, a gang's faction), so it no longer tries to grind rep there.
- **`node-eta.js` no longer locks in "hacking" before Bladeburner has ever been measured.**
- **`utils/notify.js` was missing from three orchestrator file lists**, so scripts using it could fail off home. Added; `orchestrator.js` also launches `city-pass.js`. Restart it with `kill orchestrator.js` then `run orchestrator.js`.

- **Darknet** (`scout.js`, `lib-auth.js`, `darkweb.js`, `clean-intel.js`): scout spreading fixed, intel files cleaned so they stop filling home, and a NIL probe added.
